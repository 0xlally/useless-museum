# 为什么 Lux3D 是"无限增长的博物馆"的前提

> 一句话：观众的问题是无限的，手工建模的产能是线性的；只有把"一句话 → 一件可旋转的三维资产"变成生产流程，博物馆才可能持续增建。Lux3D 在这条流程里不是装饰，而是生产设备。

本文是参赛论证与技术说明的主文档。实现细节见 [参赛记录](competition.md)，接口契约见 [服务端交接](server-notes.md)。

## 1. 问题设定：展品数量由观众决定

本项目的展品不是预设的六件，而是一条规则：

> 观众提出一个不值得解决的日常困扰 → 博物馆为它造一件专属的荒诞科学仪器 → 仪器作为独立 3D 资产入藏。

这条规则一旦成立，就会产生三个硬约束：

1. **数量无界**：展品数 = 观众数 × 每人问题数。下一件展品在观众开口之前不存在。
2. **语义长尾**：影子、哈欠、冷咖啡、灰尘、迟到、周一……每个问题指向不同的物件、结构与材料隐喻，无法用有限预制件拼装。
3. **展陈标准**：博物馆要求每件展品都能被旋转、缩放、检视、下载和归档，而不是一张图或一段视频。

因此，问题不是"如何把六件展品做得更好看"，而是"如何让第 7 件、第 70 件、第 700 件展品以可接受的成本出现"。

## 2. 手工建模为什么无法承担这条规则

把一件概念装置做到可展陈的 3D 资产，需要建模、拓扑、UV、贴图、材质、灯光适配与导出；行业里通常以人日计，而不是以分钟计。更关键的是它具有**线性产能**：

- 第 1 件和第 1000 件需要同样的工时；
- 新增一种语义（比如"把周一的困意折叠起来"）就要新增一套造型工作；
- 现场观众提出问题时，建模师不可能在展台旁等待；
- 资产还要满足网页加载、PBR 材质、可下载等工程约束。

这与"观众说一句话就多一件展品"的规则直接冲突。**手工建模不是做得慢，而是它的产能曲线与需求曲线永远无法相交。**

## 3. Lux3D 在生产链中的位置

```text
观众的一句话
   │  （原始需求保留，不翻译成通用模板）
   ▼
服务端造型脚本：把语义映射成"单件、连通、可生成"的仪器描述
   │  （黄铜 / 象牙白珐琅 / 明确的机械隐喻）
   ▼
Aholo Lux3D G1 文生 3D：真实异步任务，100k 面，PBR
   │
   ▼
GLB 下载 → 文件头校验 → 本地缓存 → SHA-256 登记
   │
   ▼
Three.js 展柜：旋转 / 缩放 / 线框 / 法线 / 贴图检视 / 下载
```

人工在这条链里负责**艺术指导与策展**（什么问题值得入藏、造型语法是否成立、结果是否可信），不负责**逐件建模**。这是关键区别：工作量从"每件展品 × 建模工时"变成"一套提示词语法 + 一次生成等待"。

如果没有 Lux3D，这条链在第三步就断了：

- 保留前两步，只能得到文字描述，不是展品；
- 保留后两步，只能反复展示同一批预制模型，博物馆停止增长；
- 所以 Lux3D 不是给成品加的一层特效，而是"每句话都能成为藏品"这一因果关系的必要条件。

## 4. 当前版本的证据

### 4.1 六件常设展品全部为真实 Lux3D 资产

| 展品 | 官方任务 | 原始 GLB | 浏览版 | 三角面 |
| --- | --- | --- | --- | --- |
| 影子限长器 | #4477428 | 7.37 MB | 607 KB | 96,729 |
| 哈欠收纳罐 | #4505646 | 6.62 MB | 779 KB | 99,360 |
| 冷咖啡二次杯套 | #4506067 | 6.65 MB | 669 KB | 96,851 |
| 灰尘队列整理机 | #4506171 | 6.79 MB | 436 KB | 99,039 |
| 马上到等待计时器 | #4506245 | 9.43 MB | 897 KB | 94,391 |
| 周一暂停按钮 | #4506327 | 9.26 MB | 783 KB | 97,556 |

合计：原始 48.36 MB，浏览版 4.27 MB（约 11.3×），583,926 个三角面。

> 本表由 `node scripts/verify-assets.mjs` 从实际缓存文件重新计算；`data/provenance.json` 保存完整的任务号、字节数、SHA-256、三角面数与贴图数量。

核验方式：

```powershell
node scripts/verify-assets.mjs   # 校验文件头、哈希并重写 provenance
curl http://127.0.0.1:8787/api/provenance
```

浏览器内每件展品的「藏品档案」也会展示官方任务编号、原始字节数、缓存时间与完整 SHA-256；`/api/provenance` 返回同一组数据，供评委或脚本独立核对。

### 4.2 "任意一句话"仍然成立

预设六件只是种子藏品。运行中的服务对任意问题执行同一套流程：

- `POST /api/generations` → 真实创建任务 → 轮询 → 缓存 GLB → 新展品入藏；
- 失败、取消、未配置、并发限制都有明确状态，不用假模型冒充成功；
- 页面刷新后可恢复进行中的任务；
- 观众生成的作品与常设展品使用同一套检视、下载和来源标注。

这条路径已经在开发中真实跑通（六件常设展品全部由它产生）。现场演示时建议只创建 1 个新任务，其余展示已缓存资产，避免重复消耗额度。

### 4.3 唯一性与"手工做不过来"

六件展品的轮廓、结构、材料关系完全不同：环形测量框、密封罐、杯套护甲、栅格编目机、无终点表盘、弹簧按钮。它们不是同一模型换贴图，而是由不同语义驱动的不同几何体。这正好证明：**当语义变化时，资产必须重新生成；而这正是手工产能无法覆盖的部分。**

## 5. 本轮技术优化

| 优化 | 之前 | 现在 | 目的 |
| --- | --- | --- | --- |
| 浏览资产体积 | 单件 6.6–9.4 MB | 单件约 0.4–0.9 MB（Meshopt + WebP + 1024 贴图） | 空间总览一次加载六件从 48 MB 降到 4.3 MB |
| 原始资产 | 只有一份 | 原始 GLB 保留用于下载，`/models/<id>.glb` 自动返回轻量浏览版 | 不牺牲可下载的权威资产 |
| 缓存策略 | 无长缓存 | 模型路由 `immutable`，文件名即生成 UUID | 反复切换展品不重复下载 |
| 空间总览 | 始终显示程序化占位模型 | 异步替换为真实 Lux3D 模型，失败才回退 | 总览也能证明是真实资产 |
| 资产证据 | 任务号与字节数 | 增加 SHA-256、缓存时间、`/api/provenance`、`scripts/verify-assets.mjs` | 可独立核验，不靠口头声明 |
| 展签 | 只有来源文字 | 档案内展示任务号、原始大小、缓存时间、完整哈希与两种下载 | 评委可当场核对 |
| 移动端 | 检视面板与模型争空间 | 小屏隐藏检视面板，保留来源与档案 | 展品优先 |

生成端到端的工程约束没有变：密钥只在服务端；创建请求不自动重试；临时官方 URL 不作为长期依赖；模型域名允许列表与下载上限保留。

## 6. 下一步优化路线

### P0：提交前必须完成

1. **补齐六件常设展品的真实生成**：已完成，`verify:assets` 与 `optimize:models` 均已重跑；提交前只需重新核对一次性证据。
2. **公开部署与访问控制**：给生成接口加登录/邀请码与额度限制；不要把消耗额度的接口直接暴露给陌生人。
3. **演示视频**：按 [参赛记录](competition.md) 的脚本录制真实运行画面，生成等待必须明示剪辑。

### P1：让"无限增长"更可信

1. **造型语法的可解释性**：把关键词规则升级为"语义轴 + 确定性种子"（材料、机构、时代、尺度），让同一问题可复现、不同问题更明显地分叉；仍不冒充大语言模型。
2. **生成质量门槛**：对返回 GLB 做自动检查（网格数、包围盒、NaN、贴图缺失、面数），不合格时给出可解释的重试建议，而不是直接入藏。
3. **批量与队列**：支持策展人预生成一批种子藏品，前台只做单任务；后台队列与失败重试要和"创建不重试"的计费安全策略分开。
4. **资产派生流水线**：把 `optimize:models` 接入缓存完成事件，自动生成浏览版、缩略图与 LOD；目前是手动脚本。

### P2：规模与体验

1. **按需加载**：空间总览先加载当前排，走近再加载下一排；配合 `IntersectionObserver` 与低优先级 fetch。
2. **资产 CDN / 对象存储**：模型与缩略图迁到静态存储，服务端只保留任务与来源记录；公开部署时给下载加签名 URL。
3. **检索与策展**：按问题语义、材料、形状聚类，让"无限增长"不只是数量增长，也能被浏览和理解。
4. **生成指标**：记录创建成功率、P50/P95 生成时长、缓存命中率、单件体积，作为后续优化的依据；这些指标目前尚未系统采集。

## 7. 边界与诚实声明

- 造型规划器是**确定性规则**，不是另一个大语言模型；它负责把问题翻译成可生成的单件仪器描述，不保证语义完全理解。
- 生成需要等待，页面不承诺"即时"；演示视频中的等待会被明确剪辑标注。
- 生成结果可能不符合预期；失败会如实显示，不用程序化模型冒充成功。
- 六件常设展品是**预先批量生成并缓存**的，不是在观众点击时实时生成；这正是"先生产、再展出"的策展流程。
- "手工建模 0 件"指常设展品的三维资产没有手工建模环节；界面、展签、空间与交互仍由人设计与实现。
- 每件生成资产的版权与传播范围须遵守 Aholo 服务条款、赛事授权协议与第三方许可。

## 8. 评委可核对的最短路径

1. 打开首页，任选一件展品，确认它是真实 Lux3D 模型。
2. 打开「藏品档案」，核对官方任务号、字节数、SHA-256。
3. 打开 `/api/provenance`，对照同一组数据。
4. 在「长期征集」提交一句自己的问题，观察真实任务进入队列。
5. 运行 `node scripts/verify-assets.mjs`，从磁盘重新计算并核对。
